# Phoenix — передача проекта в новый чат

Версия на момент записи: **3.9.54** (versionCode 66), 06.11.2026. Прочитайте этот файл целиком, потом `README.md` (история версий 3.0 → 3.9.11, раздел «Что где» там частично устарел — актуальная карта ниже).

## 1. Кто и зачем
- Пользователь (ник Hi_be, студент колледжа, сетевое/системное администрирование) делает **Phoenix** — Android-приложение (Kotlin, Compose, **интерфейс и комментарии на русском**) для телефона Xiaomi/Vivo, Android 12. Это сборщик и менеджер VPN/прокси-конфигов для России + собственный VPN-клиент на ядре **Xray** (`libv2ray.aar` кладётся в `app/libs/`, в проекте его нет).
- Контекст: в России блокировки двух видов — **белые списки** (открыто только российское, на мобильной сети) и **чёрные списки** (закрыто отдельное, обычно дома по Wi-Fi). Приложению нужно: собирать конфиги из ~20+ публичных источников, находить рабочие, подбирать сервер под конкретные приложения/сервисы (Claude, Qwen, DeepSeek, Telegram, YouTube, Steam…), держать российские приложения мимо VPN.
- Как общаться: по-русски, коротко, по делу. Пользователь присылает журналы (`phoenix-log`, `phoenix-diagnostics`) и скриншоты; обычно просит «продолжай». Любые правки поставляются **zip-архивом проекта** (`phoenix-android.zip`) + строка в README про версию. Разработка идёт без Android Studio у меня: Android-код не собирается, только проверяется (см. §6). Пользователь сам собирает и ставит.

## 2. Карта кода (`app/src/main/java/com/phoenix/app`)
Сбор конфигов (ночной / раз в N часов; пользователь выставил **каждые 6 часов**):
- `Scheduler.kt` (+`Schedule.kt` чистая логика) — будильник + WorkManager + «догон». `PhoenixWorker` → `Collector` по каждому включённому режиму → при успехе `Recheck.enqueueIfDue` (иначе `TargetsWorker.enqueue`).
- `Collector.kt` — конвейер: список источников → blacklist → загрузка → аудит → `Dedup` (топ-3 на адрес) → `Enricher` (страна) → `Tracker` → `Report`. `SourceState.kt` — жизненный цикл источника (5 неудач подряд → блок на неделю; если не ответил НИ ОДИН источник — счётчики не меняются).
- `SourceAudit.kt`, `SourceStats.kt` (`AutoPriority` — автоприоритеты источников по доле живых), `UserSources.kt`, `Enricher.kt` + `GeoIpDb.kt` (+`assets/geoip4.bin`, таблица стран IPv4 из RIR, CC0/NRO; без обращений в сеть), `NameGeo.kt`, `LinkParser.kt`, `ConfigIdentity.kt` (личность конфига = протокол + нормализованное имя, иначе адрес).
- `Storage.kt`, `Mode.kt`, `Repository.kt`, `Backup.kt` (текстовый бэкап; переносит цели, обход, свои источники, выбранные/убранные/свои сервисы, ручные приоритеты, исключения автообхода, опыт).

Проверки и выбор серверов:
- `ServerSearch.kt`, `Recheck.kt` (`SearchPool`, `Recheck.runAll`: TCP-отсев → задержка через ядро → сервисы → `DirectProbe` → `AutoPriority` → цели), `Baseline.kt` (замер задержки, Cloudflare-запасной URL), `ServiceCheck.kt` (`ServiceChecker`: TG/QW/CL/YT/ST + ≈ «частично», GeoGate по стране выхода), `ServiceBlocks.kt` (`GeoGate`: закрытые страны; для Claude/OpenAI ещё HK/MO — список из памяти, править там), `SpeedRunner.kt`, `SpeedTest.kt`, `AutoServices.kt`.
- 3.9.15: сервер, выбранный вручную, закреплён (`manualPinLink` в `PhoenixVpn.kt`): автоперебор его не меняет, пока ядро работает (раньше telegram-only уходил через 2 с из-за общей проверки). Шанс работы приложения (`ServiceOdds.kt`, история `service_history.tsv` рядом с `service_checks.tsv`, пишет `CheckStore.putAll`, читает `CheckStore.odds()`) показан в карточке конфига: «Claude 85% ✓». Кнопка «Только приложения» (`Recheck.runServices`, `AutoServices.run(all=true)`).
- Выбор сервера вручную (3.9.14): «Сменить сервер» (кнопка, уведомление, плитка `SwitchTileService`, виджет `PhoenixWidgetProvider`) открывает приложение с флагом `SwitchRequest.EXTRA_SHOW` → `ServerSwitchHost` (`SwitchUi.kt`) показывает список из `ServerChoice.options` (чистая логика в `ServerChoice.kt`); выбор → `PhoenixVpnService.switchTo` → `switchTo()` (двойная проверка `tunnelWorks`, при неудаче возврат на прежний). «Автоматически» = старый `ACTION_SWITCH`. В `ServerChoice.kt` же `FailoverGate` и `RecheckGuard`.
- Принудительная смена сервера: `PhoenixVpnService.switchServer` → `ACTION_SWITCH` → `failover(forced = true)` (журнал `SWITCH`). `Recheck.runAll(withForeign=…)`: вручную только свой режим, авто в чёрных списках — со своими+белыми.
- `Targets.kt` (`KnownApps`, `TargetStore`, `Ranking`, `Soft`, `TargetVerifier`, `PlanBuilder`), `TargetsWorker.kt` — «цели» (приложение/сайт → свои серверы). Вариант **А**: маршрут по приложению на отдельный сервер; вариант **Б**: переключение всего VPN при открытии приложения (нужен доступ к статистике использования).
- `BypassApps.kt`, `DirectCatalog.kt`/`DirectProbe.kt` (автообход: что напрямую открывается — идёт мимо VPN), `RussianApps.discover` (автопоиск установленных российских приложений).

VPN и режимы:
- `PhoenixVpn.kt` — `PhoenixVpnService`: TUN, ядро, 8 мониторов (здоровье, смена плана, вариант Б, тип блокировок раз в 5 мин, скорость, маршруты…), failover, `switchToModeServer`, `opLock` Mutex. Собственное приложение исключено из VPN.
- `XrayConfig.kt` (ссылка → конфиг; внутренний SOCKS **с паролем**), `XrayCore.kt` (рефлексия над libv2ray), `LocalSocks.kt` (**свой SOCKS5-клиент с паролем + HTTP GET**, т.к. HttpURLConnection на Android не умеет SOCKS-пароль), `Hosts.kt` (`LocalProxy`).
- `BlockDetector.kt` (`ModeDecider`, `ModeHold` — пауза автоопределения 30 мин после ручного выбора; с 3.9.40 снимается сменой сети и 4 одинаковыми противоречащими определениями), `ModeDetector.kt` (замер по физической сети), `NetInfo.kt`, `SlowMonitor.kt`, `ForegroundWatcher.kt`.

Интерфейс: `MainActivity.kt` (ViewModel), `VpnScreen.kt`, `SettingsScreens.kt` (в т.ч. Диагностика/Сводка/Журнал), `Diagnostics.kt` (`redact` — вычищает ключи и токены при копировании журнала), `Report.kt`, `PhoenixTile.kt`.

- **Стабильность (3.9.44):** `ProbeShare.kt` — одинаковые замеры «конфиг × адрес» из разных задач (перепроверка, цели, сервисы, смена сервера) выполняются один раз, свежий результат (20 с, неудача 5 с) переиспользуется; `PhoenixVpn`: если hev остановился посреди сессии, служба сама переходит на встроенный движок до конца сессии (`hevActive`/`hevCrashed`); проверка сервисов целей использует `GovernedLimits`. Сворачивание пропущенных запусков уже обеспечено: сбор — один «догон» на слот (`Schedule.catchUpNeeded`), периодические задачи WorkManager не накапливаются.
- Журнал, новые теги: `FETCH`, `SCHED`, `ANR`, `PAGE`, `MODE` (строка про снятие удержания), `FAILOVER` (контекст приложения/сайта).

## 3. Ключевые решения и почему
- Статус сервиса: ✓ работает, ≈ частично (soft-проверка: любой HTTP-ответ дошёл, но не 200), ✗ нет. Для Claude строгая проверка + страна выхода через Cloudflare trace (HK/MO считаются закрытыми).
- Порядок кандидатов: ✓, ≈, непроверенные, ✗; серверы закрытой страны — только если нет замеров.
- Проверки привязаны к **выбранным пользователем сервисам** (`selectedServiceIds`).
- Определение режима: по физической сети; смена режима требует 2 одинаковых результата подряд, переход в белые списки подтверждается 45 с (ложные срабатывания при сбое Wi-Fi). Ручной выбор режима отключает автоопределение на 30 мин или до смены сети.
- Источники с автоприоритетом (относительные пороги); ручные приоритеты главнее.
- Автообход: запись попадает «через VPN» только после 2 подряд неудач прямого доступа; пользователь может исключить автодобавленное.

## 4. Что известно про среду пользователя
- Сети: домашний Wi-Fi (чёрные списки, 5/6 зарубежных открываются) и мобильная МегаФон (иногда белые списки: 0–1/6 зарубежных). Журналы показывают частые смены wifi ↔ mobile ↔ none.
- Телефоны: Xiaomi (MIUI/HyperOS), также Vivo (OriginOS) — агрессивная экономия батареи, задачи «прерывает система».
- Источники конфигов: список в `Collector.SOURCES_LIST_URL` + свои; часть — личные подписки с токенами в URL (в журнале при отправке они маскируются).

## 5. Открытые вопросы / не проверено на устройстве
1. **`LocalSocks` по HTTPS** (проверка здоровья, скорость, страна выхода, soft-проверка) проверен на JVM только по HTTP на игрушечном SOCKS-сервере. На телефоне смотреть строки `SVC` (должны быть ✓), `HEALTH`, `TARGET`. Если все проверки стали ✗ — сначала подозревать его (TLS поверх `createSocket(sock, host, port, true)`, `endpointIdentificationAlgorithm=HTTPS`).
2. Режим «не менялся» (скриншот 14:23 18.10): исправлены причины (ручной выбор откатывался автоопределением; замер по неверной сети), но на живых данных после 3.9.8+ не подтверждено. Нужен свежий журнал со строками `DETECT: … (сеть …)`.
3. Страна по таблице IP — страна регистрации, у CDN может не совпадать с местом сервера; в приоритете страна из названия профиля.
4. Отложено: ротация/шифрование хранимых конфигов (лежат в приватной папке в открытом виде); будущий сервер обновлений потребует подписи списков и HTTPS (обсуждено, не делалось).
5. Аудит логики закончен по всем модулям из списка; детальный разбор `ServerSearch`, `SpeedTest`, `TargetsWorker` делался раньше и покрыт тестами.

## 8а. Что точно не будем добавлять и зачем
- **Телеметрия (Sentry/Firebase и т. п.)** — приложение ничего не отправляет наружу, кроме запросов за конфигами; это принципиально для приватности. Вместо этого — локальный журнал и отчёт, который пользователь присылает сам.
- **Шифрование настроек/бэкапа «ключом приложения»** — данные в приватной папке приложения, ключ лежал бы рядом: защиты нет, а сложность и риск потерять бэкап есть. Токены в ссылках лучше маскировать в журнале и отчётах.
- **UI-тесты на эмуляторе / CI** — здесь нельзя запустить Android; такие тесты не заменяют проверку на живых телефонах. Логика покрыта чистым харнессом (`tools/kt-harness`).
- **Знание о других устройствах/роутере из приложения** — приложение не видит чужие устройства и настройки роутера; можно только осторожно мерить свою сторону (потери, jitter).
- **Автовыбор hev/встроенного движка по бенчмарку** — замер скорости на мобильной сети слишком шумный; выбор остаётся ручным, с автоматическим откатом на встроенный при сбое.
- **Новый «NetworkLoadController» с нуля** — без проверки на устройстве слишком рискованно. Вместо этого оставшиеся пути подключаем к уже существующим ограничителям (`ParallelGovernor`, `AdaptiveGate`).
- **QR-сканер, проверка ASN, откат MTU до 1400, «режим минимализма»** — нужны камера/внешние данные или результат нельзя проверить без устройства; пользы меньше, чем риска.
- **Из экспорта Gemini:** domain fronting/маскировка под легитимный трафик (ломается без серверной части, которой у нас нет), SQLCipher/шифрованная БД (данные в приватной папке; ключ лежал бы рядом), миграция на Kotlin Multiplatform, изоляция Xray в отдельном процессе (риск для VpnService без возможности проверить), облачная раздача конфигов (нужен сервер, приватность), Always-on/Tasker Intent API и геотриггеры по Wi-Fi (нужны разрешения и проверка на устройстве — максимум «позже»).
- **Предложения без исходного кода** (в присланных текстах описаны изменения 3.9.31–3.9.38, но кода нет) — принимаем как идеи, не как факты о проекте.

## 8г. Уже исправлено — не предлагать повторно (на 3.9.54)
- **ProbeShare:** ключ = SHA-256 конфига + URL; после тайм-аута повторяет один из ожидающих; ≤2048 завершённых записей, просроченные удаляются, `saved` атомарный (3.9.48, 3.9.50).
- **Collector:** счётчики источников атомарные; кэш и метки обновления удалённых источников удаляются; заблокированные не трогаются (3.9.50–3.9.51).
- **ServerSearch:** возвращает ≤`want` быстрейших; `OFFLINE_SUSPECT` = 120 отказов **и** ≥40 разных host:port (3.9.49–3.9.50).
- **Recheck при «нет интернета»/прерывании:** `AutoServices`, `DirectProbe`, приоритеты и `TargetsWorker` не запускаются; `TCP_FAIL` не пишется в `ConfigHistory`, если сеть явно лежала (3.9.48–3.9.49).
- **HEALTH:** пропуск при занятом `opLock`; результат отбрасывается, если ядро перезапускали (`coreGen`) (3.9.48–3.9.49).
- **ANR при «Копировать» журнал:** `redact` в IO (3.9.48).
- **Chrome/цели без своего сервиса:** узкоспециализированные серверы (≥3 измеренных сервиса, ни один не открыт) идут после остальных; учитываются только свежие (≤3 дня) результаты без смены адреса (3.9.48–3.9.49).
- **Gemini/NotebookLM:** `RegionBlock` смотрит и в параметры адреса (`location=unsupported`); длинные заголовки ответа не обрывают чтение (3.9.45, 3.9.51).
- **Android 10–12:** `InputStream.readNBytes` заменён на `readUpTo` (3.9.51); `disconnect()` в `finally`.
- **Приватность:** отчёт `report.txt` маскирует токены (запись, показ, экспорт) (3.9.51).
- **Планировщик:** повтор через 10/30 мин после сбоя/нет сети; догоняющий сбор при появлении сети (3.9.45).
- **3.9.52:** выбор сервера при автоподключении/плитке не на главном потоке; импорт «Поделиться» с лимитами; `ParallelGovernor` считает активные прогоны; первый `onAvailable` не теряется; кэш DNS чистится при смене сети и пробует до 3 IP; `Json.looksLikeObject` проверяет вид скобок; `ExitLog` берёт 30 записей.
- **3.9.53:** прямой маршрут цели не считается рабочим сервером в строке `TARGET:`; запасной сервер без фиктивных «0 мс».

## 8д. Типичные ложные тревоги (не считать дефектами Phoenix)
- **«Тесты не запускаются / нет `K2JVMCompiler`»** — в среде аудитора нет `kotlin-compiler-embeddable-2.0.21.jar`. Это не ошибка проекта; число тестов (`ALL OK (N)`) — заявленное, повторить можно только с этим jar.
- **`libv2ray.aar` отсутствует в архиве** — так задумано (лицензия/размер), лежит только `app/libs/README`; поведение Xray по исходникам не проверить.
- **Журнал старше исходников.** Последняя запись `ENV: Phoenix X` показывает версию, на которой он снят; исправления более поздних версий по нему не проверяются. Всегда сравнивайте версию журнала с `versionName`.
- **PDF «3.9.25» с описанием 3.9.47** — имя файла устарело, содержимое актуально по тексту.
- **`HEALTH: нет связи` ≈ 1300 записей, восстановление ≈ 220** — не 1300 отказов туннеля: большая часть — кратковременные сбои сети, которые проходят сами (иногда за 4 с); защита от ложного failover сознательная.
- **`TARGET: … первый [] …` при прямом маршруте (DeepSeek)** — штатный fallback `Target.DIRECT`, а не пустой список.
- **`SHADOW: по рейтингу первый […], по оценке обучения […] (выбор не менялся)`** — только запись для сравнения, на выбор не влияет.
- **`checked 0` у запасного сервера, найденного заранее** — нового поиска не было, но туннель после запуска перепроверяется (`tunnelWorks`).
- **22 записи `EXIT: не хватает памяти` (27–29.10)** — версии 3.9.31–3.9.36; позже не повторялись.
- **`SMART:` 06:03, 06:07, 06:08** — нажатия пользователя (кнопка, плитка), не самопроизвольный цикл смен.
- **Wi-Fi «подключён, но интернета нет»** — `NetInfo.label` остаётся `wifi`; это известная особенность, `DETECT: нет сети` — отдельная строка.
- **`syntax: 0` из `syn.sh`** — проверка только синтаксиса (около 4000 «unresolved reference» на Android-классы ожидаемы), не компиляции Android.

## 8е. Правила для аудитора (что требуется от находки)
1. Прочитайте `docs/HANDOFF.md` и `README.md` целиком до первой находки; сверьтесь с 8а, 8в, 8г, 8д.
2. Каждая находка: `файл → функция → строки`, метка [КОД] / [ЖУРНАЛ: строка и время] / [ГИПОТЕЗА — какой замер нужен]. Нет доказательства — «не проверено».
3. Не предлагайте то, что в 8а/8в, без новых доказательств (нового журнала или кода).
4. Перед утверждением «этого нет» ищите по всему проекту (`grep`), а не только в одном файле; проверяйте, что файл той версии, что в `versionName`.
5. Для Android-кода сверяйте API-уровень: `minSdk = 29`, `compileSdk = 35` (методы Java 11+ вроде `readNBytes` на Android 12 недоступны).
6. Различайте: «ошибка в коде» (воспроизводима тестом), «ошибка в данных/сети» (журнал), «ограничение среды аудитора» (нет jar/aar/устройства).
7. Для каждого исправления: минимальный патч, тест чистой логики (если возможен), строка журнала, по которой пользователь убедится на телефоне.
8. Не выдавайте описание за готовый патч. Если файлы изменить нельзя — так и скажите.

## 8ж. Инварианты — не ломать любой правкой
1. **Переключение ядра:** только под `opLock`; `switching` выставлен; `coreGen` растёт до и после `reloadCore`; проверка `HEALTH` с устаревшим поколением отбрасывается.
2. **ProbeShare:** один ключ (SHA-256 конфига + URL) — максимум один активный замер; ожидающие получают один результат; просроченные и лишние завершённые записи удаляются, идущие — никогда.
3. **Главный поток:** никакого чтения всех конфигов, рейтинга, `redact`, сетевых запросов и многократной записи файлов (выбор сервера — в потоке/IO; импорт — пакетом).
4. **Сеть лежала ≠ сервер мёртв:** `TCP_FAIL` при `suspectedOffline`/`offlineRecently` не пишется в `ConfigHistory`; после прерванной перепроверки не запускать `AutoServices`/`DirectProbe`/приоритеты/`TargetsWorker`.
5. **Нагрузка:** тяжёлые пути проходят через `ParallelGovernor`/`AdaptiveGate`/`CheckLimits`; параллельность не увеличивать без журнала; `GovernedLimits` разделяются между подсистемами.
6. **Приватность:** любой адрес источника в журнале и отчёте — через `LogMask`; в сообщениях об ошибках не печатать токены; бэкап — единственное место, где ссылки как есть (предупреждать пользователя).
7. **Совместимость:** `minSdk 29`, нельзя Java 11+ API без `Build.VERSION`-проверки (`readNBytes` и т. п.; Kotlin-аналоги вроде `isBlank()` безопасны).
8. **Неизвестное ≠ плохое:** результат проверки без данных — нейтральный; «не открылось» только при подтверждённом ответе/таймауте в рабочей сети.
9. **Свежесть результатов:** `staleFor(link)` (смена адреса) и возраст (≤3 дня для `narrow`, 20 с/5 с для ProbeShare) учитывать при использовании сохранённых проверок.
10. **Журнал и файлы:** запись в `phoenix-log.txt` — под общим замком по пути файла (`Storage.lockFor`); файлы состояния — `writeTextAtomic`.

## 8и. Процесс и ошибки, которые уже были (не повторять)
- **ProbeShare, ключ по `length + hashCode`** (3.9.44) — коллизии; исправлено SHA-256. Урок: ключ кэша — полный отпечаток.
- **Неполное исправление ANR** (3.9.42): «В файл» ушла в фон, «Копировать» осталась на главном потоке. Урок: после правки искать все соседние места с тем же вызовом.
- **HEALTH-защита по `isLocked`** (3.9.48) — моментальный снимок, а не синхронизация; нужен `coreGen`. Урок: проверка состояния без блокировки не закрывает гонку.
- **`readNBytes` вернулся** (3.9.39 → 3.9.51), хотя урок был записан. Урок: перед релизом `grep -rn "readNBytes\|java.util.Optional\|\.readAllBytes\|Files.readString"` на API выше Android 10.
- **Харнесс:** в заглушках JUnit нет `assertNotEquals` и `fail` (использовать `assertTrue(a != b)`, `throw AssertionError`); тест `SearchTest.findsTheFewWorkingAmongMany` иногда мигает — при повторе проходит. Чистый харнесс не доказывает, что Android-код компилируется.
- **Атрибуция идей:** в экспортах разных моделей (GPT, DeepSeek, Gemini) идеи различаются; не приписывать предложения другой модели.
- **Скрипты правок:** `python3 -I patch.py` с `assert s.count(a) == 1`; после правки — `syn.sh` (`syntax: 0`) и `run.sh` (`ALL OK`).
- **Не читать вполсилы:** присланные пользователем файлы с аудитами читать до конца и сверять утверждения по коду (история: пропущенный остаток последнего файла в 3.9.51).
